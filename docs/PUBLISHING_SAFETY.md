## What the workflow verifies

1. Resource JSON schema, official URL formatting and catalog IDs.
2. Static catalog entries and their official provider links.
3. Story and guide references, AI discovery metadata, sitemap locations and public contribution warnings.
4. Browser JavaScript syntax.
5. Absence of designated patient-data directories.
6. A strict allowlist of public files generated by `scripts/prepare_pages.py`, with same-site HTML links and anchors checked.
7. Upload of the approved `dist/` artifact, followed by GitHub Pages deployment only if validation passed and the `PAGES_ACTIONS_READY` release switch is set to `true`.

Never add patient records, credentials, licensed private datasets or other sensitive data to the repository: the repository itself is public, even though the deployed artifact has a narrower allowlist.

## Remaining safeguard: protect `main`

As of November 7, 2026, the GitHub API reports `main.protected = false` and no repository rulesets. The connected GitHub integration does not offer a branch-rules editing action, so **this step requires the repository owner in GitHub Settings**.

1. Open https://github.com/davidwpace/open-biomedical-resource-center/settings/rules .
2. Create a branch ruleset targeting **`main`** (or use Settings → Branches → Add branch protection rule if preferred).
3. Require a pull request before merging and require the exact status check **`Catalog & syntax checks`**. Enable the rule rather than leaving it in evaluation-only mode.
4. Consider preventing force pushes/deletion and requiring one review if you have collaborators. If solo, confirm the rule permits your intended owner merge flow and doesn't lock you out.
5. Verify the rule applies by opening a test pull request and confirming GitHub blocks merging until checks succeed.

**Important:** Branch protection prevents bypassing the validated merge process; the active Actions dependency already prevents publishing when the validation job fails. These are complementary safeguards.

## Normal workflow for contributors

1. Propose changes on a feature branch; do not edit `main` directly.
2. Create a pull request; check that `Catalog & syntax checks` passes.
3. Review research sources, privacy disclosures and generated pages; merge when acceptable.
4. Confirm the resulting `main` workflow runs **Catalog & syntax checks** followed by **Deploy approved site**.
5. Test published website navigation on mobile. GitHub's successful deployment is evidence of publication, not an independent real-browser accessibility test.

## Emergency pause or rollback

- To **pause automatic deployment**, set repository variable `PAGES_ACTIONS_READY=false` under Settings → Secrets and variables → Actions. The validated code stays available in GitHub; Pages should continue serving the last successful deployment.
- To **restore deployments**, set it to `true` and run **Actions → Validate public directory → Run workflow → main**.
- Do **not** switch Pages Source back to branch publishing unless a deliberate recovery is required; doing so removes the fail-closed dependency.
